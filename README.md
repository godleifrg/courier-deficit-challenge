# Прогноз дефицита курьеров

Решение прогнозирует для каждого даркстора дефицит курьеров на неделю,
начинающуюся 24 ноября 2025 года. Целевая переменная `target` — неотрицательное
количество курьеров, которых требуется дополнительно нанять.

Финальный прогноз — округлённое среднее пяти моделей CatBoost, обученных с
разными `random_seed`. Качество и постобработка выбраны по двум последовательным
временным фолдам.

**В самом начале советую пройтись по файлу eda.ipynb, там я сделал первоначальный анализ данных и в самой первой ячейке написал много своих мыслей насчет будущих исследований и вопросов к данным**

## Состав папки

- `train.py` — автономный скрипт загрузки данных, построения признаков,
  временной валидации, обучения ансамбля и формирования submission;
- `submission.csv` — готовый прогноз для отправки;
- `eda.ipynb` — исследовательский анализ данных;
- `requirements.txt` — зафиксированные версии библиотек.

Исходные `train.csv`, `test.csv`, `facts.csv` и `shifts_prediction.csv`
передаются скрипту через параметр `--data-dir`.

## Общая схема решения

1. `facts.csv` и `shifts_prediction.csv` объединяются по
   `calendar_dt, store_id`.
2. История формируется точным сдвигом календарной даты на целое число недель.
   Поэтому лаг относится к тому же даркстору и той же календарной неделе в
   прошлом, а не к предыдущей строке таблицы.
3. К фактическим и прогнозным значениям добавляются лаги, изменения,
   отношения и агрегаты по истории.
4. Для train присоединяется `target`, а для test устанавливается дата
   `2025-11-24`.
5. На двух временных фолдах обучаются пять CatBoost. Проверяются среднее и
   медиана прогнозов, округление и правило по `flag_high_load_lag_1`.
6. После выбора варианта пять моделей переобучаются на всех 8 220 строках
   train и строят прогноз для 2 438 тестовых дарксторов.

## Признаки

Всего модель получает **67 признаков**. `store_id`, `calendar_dt` и `target` в
матрицу признаков не входят. Единственный категориальный признак — `city_nm`;
CatBoost обрабатывает его напрямую. Числовые пропуски передаются CatBoost как
пропуски, а безопасное деление заменяет нулевой знаменатель на `NaN`.

### Фактическое состояние даркстора — 11 признаков

Значения из `facts.csv`, доступные на дату построения прогноза:

- `fact_staff_value_lag_1` — фактически необходимый штат за прошлую неделю;
- `fact_load_factor_lag_1` — фактическая нагрузка;
- `num_available_couriers_lag_1` — доступные курьеры;
- `fact_num_orders_lag_1` — фактическое число заказов;
- `fact_percent_lateness_lag_1` — доля опозданий;
- `fact_staff_churn` — показатель оттока или изменения штата;
- `fact_couriers_with_shifts_lag_1` — курьеры, вышедшие на смены;
- `flag_high_load_lag_1` — индикатор повышенной нагрузки;
- `marketing_costs_lag_1` — расходы на маркетинг;
- `store_lifetime_in_days` — возраст даркстора;
- `city_nm` — город.

### Дополнительная история фактов — 8 признаков

Для восьми операционных показателей строится ещё один недельный лаг с
префиксом `history_`:

```text
fact_staff_value_lag_1
fact_load_factor_lag_1
num_available_couriers_lag_1
fact_num_orders_lag_1
fact_percent_lateness_lag_1
fact_staff_churn
flag_high_load_lag_1
fact_couriers_with_shifts_lag_1
```

Например, `history_flag_high_load_lag_1_lag_1` — значение доступного флага на
предыдущей календарной неделе. Для этих же восьми колонок рассчитывается
изменение относительно прошлой недели: `<column>_diff_1`.

### Производные признаки по фактам — 12 признаков

- `fact_staff_gap_available` = необходимый штат − доступные курьеры;
- `fact_staff_gap_with_shifts` = необходимый штат − курьеры на сменах;
- `shift_participation_rate` = курьеры на сменах / доступные курьеры;
- `orders_per_available_courier` = заказы / доступные курьеры;
- восемь недельных разностей `<column>_diff_1` для показателей из предыдущего
  раздела.

### Прогнозы внешней системы — 27 признаков

Используются три исходных прогноза из `shifts_prediction.csv`:

- `predicted_staff_value`;
- `predicted_num_orders`;
- `predicted_load_factor`.

Для каждого из них строятся:

- точные недельные лаги `history_<column>_lag_1` … `_lag_4`;
- изменение к прошлой неделе `<column>_diff_1`;
- отношение к прошлой неделе `<column>_ratio_1`;
- среднее текущего значения и лагов 1–3 `<column>_mean_4`;
- стандартное отклонение текущего значения и лагов 1–3 `<column>_std_4`.

Текущее значение, четыре лага и четыре производных признака дают девять
признаков на каждый прогнозируемый показатель, всего 27.

### Взаимодействия факта и прогноза — 3 признака

- `predicted_staff_gap_available` = прогноз требуемого штата − доступные
  курьеры;
- `predicted_staff_gap_with_shifts` = прогноз требуемого штата − курьеры,
  вышедшие на смены;
- `predicted_orders_growth_vs_fact` = прогноз заказов / фактические заказы
  предыдущей недели.

### История target — 4 признака

- `target_lag_1` и `target_lag_2` — дефицит даркстора одну и две недели назад;
- `target_lag_mean_2` — среднее двух лагов;
- `target_lag_diff_1` — изменение между ними.

Лаги target создаются переносом известных значений train вперёд на одну и две
недели. Для валидационной или тестовой строки используются только уже известные
значения прошлых дат.

### Календарь — 2 признака

- `calendar_week` — номер недели ISO;
- `calendar_month` — номер месяца.

Суммарно: 11 исходных фактических + 8 дополнительных лагов фактов + 12
производных фактов + 27 признаков внешнего прогноза + 3 взаимодействия + 4
лага target + 2 календарных = **67 признаков**.

## Baseline на `fact_staff_churn`

Главной простой точкой отсчёта выбран `baseline_churn`. Он не обучает модель и
для каждой строки напрямую использует доступное значение:

```python
prediction = fact_staff_churn.fillna(0).clip(lower=0)
```
По смыслу этот показатель можно рассматривать как уже известную часть потребности в найме: если курьеры выбыли
из штата, их как минимум потребуется заместить.

Такой baseline выбран по трём причинам:

1. признак известен до прогнозируемой недели и может использоваться без
   временной утечки;
2. прогноз имеет ту же размерность, что и `target`, поэтому не требует обучения
   или подбора коэффициента;
3. в train наблюдается сильная связь с целью: корреляция равна 0,875, а в 72,2%
   строк `target` точно совпадает с `fact_staff_churn`.

На всех 8 220 обучающих строках выполняется
`target >= fact_staff_churn`. Поэтому baseline ведёт себя как эмпирическая
нижняя граница дефицита: он либо попадает точно, либо недооценивает потребность,
но не переоценивает её. Разность `target - fact_staff_churn` — это часть
дефицита, которую нужно объяснить нагрузкой, заказами, доступностью курьеров,
планами смен и другими признаками.

Результат baseline на временной валидации:

| Неделя | Сумма target | Сумма прогноза | MAE на строку | WAPE |
| --- | ---: | ---: | ---: | ---: |
| 10.11.2025 | 6 407 | 4 942 | 0,6014 | 22,8656% |
| 17.11.2025 | 6 242 | 4 753 | 0,6105 | 23,8545% |
| Оба фолда | 12 649 | 9 695 | 0,6060 | **23,3536%** |

Примерно в 70% строк каждого валидационного фолда baseline даёт точное
значение. Его основная ошибка — систематическое занижение: на двух неделях он
недопрогнозирует суммарно 2 954 курьера. CatBoost нужен, чтобы оценить
дополнительный дефицит сверх `fact_staff_churn`.

Финальный ансамбль снижает pooled WAPE с 23,3536% до 17,2108%, то есть на 6,14
процентного пункта, или примерно на 26,3% относительно ошибки baseline.

В коде также оставлен диагностический `baseline_last_target`: прогноз равен
`target_lag_1`, а для даркстора без доступного лага используется
`fact_staff_churn`. Его pooled WAPE равен 60,7558%. Это показывает, что простое
перенесение дефицита прошлой недели работает значительно хуже текущего
показателя churn и не учитывает быстрые изменения спроса и штата.

## Модель и ансамбль

Для каждого seed из набора `13, 42, 73, 101, 202` обучается независимый
`CatBoostRegressor` со следующими параметрами:

```text
loss_function = MAE
eval_metric = MAE
iterations = 300
learning_rate = 0.05
depth = 6
l2_leaf_reg = 6.0
thread_count = -1
```

Отрицательные ответы каждой модели ограничиваются нулём. После этого
проверяются два способа ансамблирования:

- среднее пяти прогнозов;
- медиана пяти прогнозов.

Для одиночных моделей и ансамблей также проверяется округление
`np.rint(prediction).clip(0)`. Оно соответствует дискретной природе количества
курьеров и заметно улучшает WAPE. Финальный вариант использует округлённое
среднее пяти seed.

## Временная валидация

Случайное разбиение для этой задачи не используется: соседние недели одного
даркстора зависимы, а обычный random split дал бы модели доступ к наблюдениям из
будущего. Вместо него применяется expanding-window validation — обучающее окно
расширяется во времени, а проверка всегда выполняется на следующей неделе.

| Фолд | Обучение | Строк train | Валидация | Строк validation |
| --- | --- | ---: | --- | ---: |
| 1 | все даты раньше 10.11.2025 | 3 345 | 10.11.2025 | 2 436 |
| 2 | все даты раньше 17.11.2025 | 5 781 | 17.11.2025 | 2 439 |

Во втором фолде неделя 10 ноября уже входит в обучение. Это имитирует реальный
процесс: перед прогнозом следующей недели становятся доступны факты и target за
предыдущую. Для финального прогноза на 24 ноября используются все строки train,
включая 17 ноября.

Метрика для каждого фолда:

```text
WAPE = sum(abs(target - prediction)) / sum(target)
```

Для выбора модели используется **pooled WAPE**: сначала абсолютные ошибки и
target суммируются по обоим фолдам, затем вычисляется их отношение. Это
взвешивает недели по суммарному дефициту и совпадает с расчётом WAPE на
объединённых out-of-fold прогнозах. Простое среднее двух недельных WAPE не
используется.

| Вариант | 10.11.2025 | 17.11.2025 | Pooled WAPE |
| --- | ---: | ---: | ---: |
| Seed 42, округление | 17,5589% | 16,7574% | **17,1634%** |
| Среднее 5 seed, округление | 17,7774% | 16,6293% | **17,2108%** |
| Медиана 5 seed, округление | 17,9335% | 16,4691% | **17,2108%** |
| Baseline `fact_staff_churn` | 22,87% | 23,85% | **23,3536%** |

Одиночный seed 42 на этих двух фолдах немного лучше среднего ансамбля. Для
финального решения выбран ансамбль: оценка одного seed на двух неделях более
чувствительна к случайности обучения, а усреднение даёт стабильный прогноз.
Среди ансамблей среднее и медиана имеют одинаковый pooled WAPE; при равенстве
код выбирает среднее.

## Проверка правила по `flag_high_load_lag_1`

В train наблюдается строгая связь: при `flag_high_load_lag_1=0` целевая
переменная также равна нулю. Чтобы проверить её практическую пользу, каждый
прогноз сравнивается со своей копией, к которой применяется правило:

```text
если flag_high_load_lag_1 == 0, prediction = 0
```

| Агрегация | Без правила | С правилом | Изменение WAPE |
| --- | ---: | ---: | ---: |
| Среднее, вещественный прогноз | 18,5752% | 18,4914% | −0,0838 п.п. |
| Медиана, вещественный прогноз | 18,4872% | 18,4468% | −0,0404 п.п. |
| Среднее, округлённый прогноз | 17,2108% | 17,2108% | 0,0000 п.п. |
| Медиана, округлённый прогноз | 17,2108% | 17,2108% | 0,0000 п.п. |

У вещественных прогнозов правило удаляет небольшие положительные значения при
нулевом флаге. После округления эти значения уже равны нулю, поэтому правило не
меняет итоговый прогноз. Gated-вариант выбирается только при строгом снижении
pooled WAPE; при равенстве остаётся вариант без жёсткого ограничения. Сам флаг,
его история и изменение продолжают использоваться как признаки модели.

Природу строгой связи следует уточнить у организаторов: это может быть
бизнес-правило расчёта дефицита или техническая особенность формирования
выборки.

## Обучение финальной модели

После валидации пять моделей с теми же параметрами обучаются на всех 8 220
строках train. Для каждой тестовой строки рассчитывается среднее пяти прогнозов,
затем результат округляется и ограничивается снизу нулём.

Готовый `submission.csv` содержит 2 438 строки в порядке
`sample_submission.csv`, без индекса и пропусков. `target` — целое

## Запуск

### Kaggle Notebook

1. Добавьте к notebook Dataset, в котором находятся `train.csv`, `test.csv`,
   `facts.csv` и `shifts_prediction.csv`.
2. Загрузите `train.py` в notebook или добавьте его как отдельный Dataset с
   кодом.
3. Выполните скрипт в ячейке.

Если код вставлен непосредственно в ячейку, достаточно выполнить её. Скрипт
сам найдёт единственный подходящий каталог внутри `/kaggle/input` и сохранит
результаты в `/kaggle/working`.

Если `train.py` подключён как файл:

```python
%run /kaggle/input/<dataset-with-code>/train.py
```

Когда в `/kaggle/input` находится несколько наборов с одноимёнными файлами,
укажите каталог данных явно:

```python
%run /kaggle/input/<dataset-with-code>/train.py \
    --data-dir /kaggle/input/<dataset-with-data> \
    --output-dir /kaggle/working
```

Jupyter передаёт Python служебные параметры вида `-f .../kernel.json`. Скрипт
разбирает только собственные параметры и игнорирует служебные, поэтому ошибка
`unrecognized arguments: -f` больше не возникает. После завершения готовый файл
находится по адресу `/kaggle/working/submission.csv`.

### Локальный запуск

Запуск из корня проекта:

```powershell
python -m pip install -r final_solution/requirements.txt
python final_solution/train.py --data-dir . --output-dir final_solution/reproduced_output
```

В `reproduced_output` будут сохранены:

- `submission.csv` — итоговый прогноз;
- `validation_results.csv` — метрики всех вариантов по датам и pooled WAPE;

  отклонение важности по пяти seed.

Код дополнительно проверяет уникальность ключей `calendar_dt, store_id`,
покрытие тестовых строк фактическими и прогнозными данными и наличие всех трёх
признаков, связанных с `flag_high_load_lag_1`.
